# Connect4 Space UI 精修設計

日期：2026-08-30  
狀態：使用者已核准  
介面：Hugging Face Space `steven0226/connect4-arena`

## 背景

現有 Gradio 介面功能正確，但視覺上接近框架預設樣式：棋盤與控制區的層級偏弱、卡片與圓角使用過多、首屏有無效空白，而且按鈕事件採 Gradio 預設 `show_progress="full"`，導致玩家每次落子後棋盤與勝率元件短暫被完整 loading 遮罩覆蓋。

本次精修保持既有模型、MCTS、遊戲規則、中文內容與橘色識別，不更換框架，也不加入裝飾性動畫。

## 目標

1. 讓偏好棋類遊戲的中老年使用者不必縮放頁面即可看清所有遊戲資訊。
2. 降低 Gradio 預設元件堆疊與初學者模板式 UI 的觀感。
3. 只在具有語意的元件使用圓角，不把每個區塊都做成圓角卡片。
4. 減少無效空白，將首屏主要面積分配給棋盤和必要控制項。
5. AI 思考期間保留棋盤與局面資訊，不再顯示覆蓋主要輸出的完整 loading 遮罩。
6. 桌機與手機都保有清楚的閱讀順序與足夠大的觸控目標。

## 非目標

- 不重訓或更換模型。
- 不修改 MCTS 強度、遊戲規則或勝率計算。
- 不新增帳號、排行榜、音效、動畫、歷史棋譜或分析圖表。
- 不改成 React、Vue 或其他前端框架。
- 不把 Space 擴張成完整遊戲平台。

## 視覺方向

採用核准的「產品化精修」方向：深藍作為棋盤與結構主色、橘色只用於主要操作與選取狀態、紅黃保留給雙方棋子。整體以直線、細框、色帶、字重與留白差建立層級。

### 字級

所有 Space 內可讀文字的計算後字級不得低於 `20px`：

- 主標題：桌機 `36px`，窄螢幕 `31px`。
- 回合狀態：`28px`。
- 關鍵勝率：`30px`。
- 說明、模型資訊、標籤、選項、按鈕及等待提示：`20–22px`。
- 落子欄位按鈕：`22px`。

Hugging Face 頁面本身的導覽列不在 Space 可控制範圍內，因此不納入此字級規則。

### 圓角與邊界

- 棋子維持圓形。
- 主要按鈕、選取狀態和落子按鈕最多使用 `4px` 圓角。
- 棋盤外框、控制區、勝率區和標題區使用直角或結構線，不使用大面積圓角卡片。
- 不使用膠囊形狀作為一般標籤或按鈕。

### 空間配置

- 主內容最大寬度約 `1240px`，置中顯示。
- 桌機採棋盤／控制區約 `1.55 : 0.95` 的雙欄配置。
- 標題、說明與模型 revision 合併為緊湊頁首，不建立獨立卡片。
- 棋盤外僅保留必要內距；七個落子按鈕直接排列於棋盤下方。
- 右側依序顯示回合狀態、局面評估、棋色、難度、新對局按鈕與等待提示，不重複資訊。
- 窄螢幕改為單欄：棋盤在上、控制區在下，不做水平捲動。

## 元件與內容

### 頁首

- 標題：「四子棋 Connect Four — 挑戰 AlphaZero」。
- 一行操作說明，直接描述選欄落子與 AI 回應。
- 保留模型 repository 與固定 revision，視覺層級低於操作說明但字級仍不少於 `20px`。

### 棋盤與落子

- 棋盤保持目前 Python renderer 的真實局面輸出。
- 棋盤容器使用單一細框，不增加卡片標題或多餘陰影。
- 七個落子按鈕高度至少 `52px`，字級 `22px`，圓角不超過 `4px`。
- 合法操作、勝負判斷與 session state 行為保持不變。

### 狀態與局面評估

- 回合狀態是右欄最醒目的文字。
- 使用者回合附上「請選擇 1–7 欄落子」的清楚提示。
- 保留 value-head 雙方機率，透過高對比結構和大字顯示，不新增模型能力宣稱。

### 選項與主要操作

- 棋色與難度使用平面分段選項；選取狀態以橘色外框、淡橘底色及字重呈現。
- 「開始新對局」是唯一實心橘色主要按鈕。
- 難度仍使用 `50 / 200 / 800` simulations，不改運算行為。

## 互動與等待狀態

- `new_game.click` 與七個落子事件不再使用預設的完整 progress overlay。
- 事件設定使用 Gradio 6.20 支援的輕量 progress 模式，使棋盤、勝率和狀態在 MCTS 執行期間保持可見。
- 等待提示必須說明 AI 正在思考，不使用無語意的全畫面 spinner。
- 不改變 callback 的輸入、輸出順序或公開 API endpoint，以避免破壞既有 smoke tests 與外部 client。
- 連續點擊仍由 Gradio queue 與既有 session state 處理；本次不引入自訂前端狀態機。

## 實作邊界

- UI 的正式來源仍是 `space/app.py`。
- 版面與 Gradio 元件設定保留在 `space/app.py`，新增一組集中管理的 CSS 字串，不建立前端建置鏈。
- `src/az` 不需要修改。
- `space/az` 仍由發布腳本從 canonical `src/az` 生成。
- `space/model_assets.py` 的模型 revision 不修改。

## 可及性與響應式要求

- 一般文字與背景的對比至少達到 WCAG AA 的實務門檻。
- 狀態不能只靠顏色傳達；必須保留文字與棋子 emoji。
- 操作目標高度至少 `48px`，落子與新對局按鈕至少 `52px`。
- 鍵盤焦點須可見，不以 CSS 移除 focus outline。
- `900px` 以下切換為單欄，所有選項不得超出 viewport。
- 在約 `390px` 寬的手機 viewport 上仍可閱讀與操作，所有遊戲內文字不少於 `20px`。

## 測試與驗收

### 自動化

1. 新增 release-boundary 測試，驗證 Space app 仍保留四個既有輸出與七個落子事件。
2. 驗證所有按鈕事件採輕量 progress 設定，避免回歸到完整輸出遮罩。
3. 驗證 UI CSS 包含 `20px` 最小字級規則、受控圓角與 `900px` 響應式斷點。
4. 既有 39 項測試全部通過。
5. 部署 dry-run 後，`space/az` 與 canonical `src/az` 必須一致。

### 視覺與互動

1. 桌機約 `1440 × 900`：主要遊戲內容在首屏內，棋盤大於控制區，沒有大片無效空白。
2. 手機約 `390 × 844`：單欄排列、無水平捲動、文字與按鈕可辨識。
3. 玩家落子時棋盤不被完整 loading 遮罩清空。
4. 新局、玩家落子、AI 回覆、勝負狀態與勝率輸出仍正常。
5. 瀏覽器 console 沒有新的錯誤。

## 發布方式

1. 本機執行 UI regression tests 與完整 pytest。
2. 使用 `scripts/deploy_space.py --dry-run` 重新生成並檢查部署 bundle。
3. 本機啟動 Space，以桌機和手機 viewport 各做一次有界視覺檢查。
4. 提交並推送 GitHub，等待 hosted CI 通過。
5. 部署既有 HF Space，不修改 model repo。
6. 對 live Space 再執行新局與落子 smoke test，確認固定模型 revision 未變。

## 完成定義

- 核准版視覺規則已落實，且所有遊戲內可讀文字的計算後字級至少 `20px`。
- 圓角只出現在棋子、選取狀態與操作元件，沒有圓角卡片堆疊。
- 桌機與手機空間利用符合驗收條件。
- 落子時不再出現覆蓋棋盤與勝率的完整 loading 畫面。
- 本機、hosted CI 與 live Space smoke tests 全部通過。
